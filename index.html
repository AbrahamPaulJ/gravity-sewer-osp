Optimal sensor placement in gravity sewers

An interactive sandbox and two explainers, built on openly published South Australian network data.

Water utilities put level sensors in sewer maintenance holes to catch blockages before they become overflows. There are far more chambers than sensors, so the question is which chambers. This is a working tool for exploring that, running on a real network rather than a synthetic one.

What is interesting here

Two things came out of building this that are worth more than the tool itself.

A published method's own parameterisation was doing most of the damage. The placement condition uses a water-depth capacity term. Substituting pipe diameter for it, which is what you do when manhole depth is not published, understates the term by roughly a factor of nineteen. That single substitution is the difference between most of the network appearing unobservable and almost none of it:

Depth used in the modelObservable universeChambers observing nothing
Pipe diameter, 0.15 m157 / 1010840 (83.2%)
Measured depth, median 2.92 m813 / 101032 (3.2%)

The invert fields are labelled by flow, not by geometry. On both publishers examined, START_INVE is the upstream-of-flow invert whichever way the line was drawn. Reading it as a geometric label silently reverses the majority of pipes while leaving every record, node and edge count identical, so the error is invisible to the usual sanity checks. Verified by testing which reading makes inverts agree at shared chambers: 95.3% exact against 35.2% and 37.0% for the alternatives.

It also means the common check START_INVE > END_INVERT returning every record is true by definition of the field names. It is a naming convention, not evidence that a network runs downhill and not evidence that it is acyclic.

Where the data comes from

Everything here is built from services that answer anonymous queries, so every figure can be re-checked independently. The network is a council's open republication of the operator's sewer asset register: 1,002 gravity mains with invert levels on every record, 360 mapped maintenance holes, and a 1 m contour layer.

Chamber depth is published almost nowhere, so it is reconstructed as cover level minus invert, with cover interpolated from those contours. That reconstruction was validated three ways and lands within about 0.23 m against surveyed values, on chamber depths of roughly 2.9 m. The assumptions tab lists every figure, every remaining assumption, and what data would remove it.

Honest limits

Nothing here has been validated against a recorded blockage: no public source lists historical chokes or overflows, so the tool can say which chambers would see a blockage under this model, not whether they did. The detection threshold is a declared parameter rather than a calibrated one, because no sensor readings for this network are public. And the network is clipped to a council boundary rather than a drainage catchment, so anything near an edge is wrong in a known direction. All of this is stated in the tool itself.
